; Each query must be fully qualified. TestController splits this on ';' and sends the
; parts as separate commands, so a bare "CURR?" - valid only as a continuation of
; "MEAS:" on one line - returns nothing and the channel silently logs no data.
#askValues MEAS:VOLT?;MEAS:CURR?;MEAS:POW?

; Track the mode the load is actually in, so a mode or range changed from the front
; panel (or by the Range control) is picked up rather than assumed.
;
; MODE? reports mode and range as one word (CCL/CCM/CCH). The range is a setting
; within the mode, not a mode of its own, so the trailing range letter is stripped
; here and the mode becomes plain CC/CV/CR/CP/BAT/OCP/OPP. That keeps the mode popup
; to one button per real mode while the Range control on each page picks L/M/H.
#askMode MODE?
#askModeMathFormat replaceRX(unQuote(value),"[LMH]$","")
#modeChangeDelay 300

#finalCmd LOAD OFF
#outputOff LOAD OFF

; A setpoint's valid span is set by the selected Range, not by the model alone: a
; 63004 in CR High accepts 64-2500 ohm, the same field in CR Low accepts 0.05-250.
; Offering the model's full span let a value be typed that the load simply ignored.
;
; The range-dependent fields therefore live on per-range pages (CC_Lo / CC_Mid /
; CC_Hi and so on) with literal limits, and the selector picks the right page from
; MODE?. An earlier attempt used advNumber with expressions referencing the Range
; control - do not go back to that. TestController raises
;     ProgramExceptions$UnknownException: Variable not found CC.Range
; because a page named by a selector is never created, so no CC.Range variable
; exists; and that exception aborts syncAll, leaving the WHOLE form blank rather
; than just the one field.

; Mode Layout and Setup

; the Range control on each page, so it does not multiply the mode buttons.

; letter, i.e. what MODE? reports reduced to its base mode. Keep the two in step.

; CR slew is a CURRENT slew, so its span follows Current Measurement Range below - NOT the resistance
; range. Verified on the instrument: identical in CRL/CRM/CRH and moving 0.0001-0.1 /
; 0.001-0.3 / 0.01-3 as RES:STAT:IRNG changes. A selector injects the matching pair.
; TestController draws only the FIRST control of a page reached through a selector
; that itself sits on a selector-inserted page. Any further control on that page is
; painted over the page being displayed, at its own item index - the setting from
; another mode appears on top of an unrelated field, and a separator becomes a line
; struck through it. Reproduced on TC V3.48 with a two-mode cut-down of this driver:
; two controls leaked one, three leaked two, one leaked none.
;
; So rise and fall each get their own selector with one control per page. Both read
; RES:STAT:IRNG? because the slew span follows the CURRENT range, not the resistance
; range. Do not merge them back into a single CR_Slew selector.
#cmdSetup selector CR_Slew_Rise CRb
:read: RES:STAT:IRNG?
:readmath: trim(unQuote(value))
:updatemodechange:

Middle CRrMid.
High CRrHi.

; The load's own discharge timer - the measurement a battery test is actually for.
;
; FETC:TIME? answers in raw seconds (4.193550), which reads as an unlabelled number
; on the form. formatHMS turns it into hh:mm:ss, so the unit is self-evident and a
; multi-hour discharge stays readable.
;
; The FETCH subsystem is query-only - there is no command to zero this. The load
; restarts the count itself each time a discharge begins, so Load off then on is the
; reset, and the tip says so rather than offering a button that cannot work.
#cmdSetup info Elapsed_Time BATb
:read: FETC:TIME?
:readmath: formatHMS(value)
:updatemodechange:
:layout:
:tip: Discharge time as hh:mm:ss, counted by the load while the input is on. It cannot be zeroed on demand - the load restarts the count at the start of each discharge, so switch Load off and on again for a fresh run.

; Protection status and reset. Without these a trip is invisible from TestController
; and can only be cleared at the front panel.
;
; LOAD:PROT? is a bitmask. The decode below only names single-bit trips, using == and
; nothing else: a readmath that throws (an unknown function, an undefined variable)
; aborts syncAll and blanks the WHOLE form, so this stays deliberately plain. Anything
; it cannot name falls through to the raw code, which is never misleading.
; Only ONE code is named below, because only one has been measured: forcing an
; over-current trip (CONF:OCP ON, limit 0.5 A, drawing 1.0 A) produces 32. An earlier
; reading of the manual's bit table predicted 8 for the same event, so that table is
; not trustworthy enough to decode from - every other code is shown as a raw number
; rather than risk naming a trip wrongly.
;
; The manual lists 11 conditions across 16 bit positions and the PDF loses the column
; alignment, so these are candidates to confirm one at a time by forcing each trip:
;   OV1 OV2 REV OCP1 OCP2 OCP3 OPP1 OPP3 OTP FAN RMT_INH
; A placement consistent with the measured 32 puts them at bits 2,3,4,5,6,7,8,10,11,13,15
; but that is inference, not evidence. Add a name here only after tripping it for real.
#cmdSetup info Protection Protection
:read: LOAD:PROT?
:readmath: value==0?"None":(value==32?"OCP - over current":value)
:updatemodechange:
:updatealloff:
:layout:
:tip: Protection status. "None" is healthy. 32 is a confirmed over-current trip; any other non-zero value is shown as the raw code - see the bit table in this driver's header. The load stays latched off until Clear Protection is pressed.

; Real-time companion to Protection above. FETCh:STATus? reports the condition as it
; is right now and clears itself when the condition goes away; LOAD:PROT? latches and
; stays set until Clear Protection. Both are useful: the latched one says what tripped
; the load, this one says whether the fault is still present.
;
; The manual prints the SAME bit table for both, so 32 is very likely over-current
; here too - but that has only been measured on LOAD:PROT?, so nothing is named. Any
; non-zero value shows as its raw code. Confirm by forcing a trip and reading both.
#cmdSetup info Live_Status Protection
:read: FETC:STAT?
:readmath: value==0?"OK":value
:updatemodechange:
:updatealloff:
:layout:
:tip: Condition right now, as a raw status code - 0 is healthy. Unlike Protection this does not latch, so it returns to OK by itself once the fault clears. See the bit table in this driver's header.
