;            GPIB reads; *CLS does not exist and ';'-joined compound commands are

#idString Guildline Instruments, 6560,
#name Guildline 6560
#handle Guildline6560
#port GPIB
#driver SCPIx
#eol \n
; The 6560 terminates replies with LF and NEVER asserts EOI (manual 4.1.9), so the
; default '++read eoi' hangs every read to the full timeout. Same fix as the stock
; Fluke8840A / Keithley199 / Racal / Yokogawa drivers.
#gpibReadEol 10
#interfaceType Calibrator
; 0.5s was too tight: confirmed live that a plain *IDN? read can
; genuinely miss a 500ms window over PrologixEthernet with this no-EOI instrument,
; producing a null read - and worse, TC then serves the STALE queued reply on the
; NEXT read, which looks like corrupted/misattributed data rather than a timeout.
; This is a ceiling, not a pacing delay (nothing here is billed on the fast path),
; so it costs nothing to be generous - the 6560 itself answers most commands in
; well under 150ms per the manual.
#readingDelay 2.5
#author Cyclotron

#notes Guildline Instruments Model 6560 Precision Resistance Calibrator / Decade Standard (0 Ω to 100 MΩ across 19 nominal standards + Open Circuit). Note that mechanical relay switching takes ~200-500 ms to actuate and settle.

; =============================================================================
; COMMUNICATION & INITIALIZATION
; =============================================================================

; *CLS does NOT exist on the 6560 (not in the manual's command list, and confirmed
; live: it sets CME in the ESR). The parser also rejects ';'-compounded commands,
; so the old '*CLS;TERSE' failed on both counts and TERSE never took effect.
; The ESR is cleared by READING it (*ESR?), not by a command.
#initCmd TERSE
; No #finalCmd: the only thing it did was *CLS, which this instrument rejects.
#outputOff RESISTOR 20000000000

; =============================================================================
; LOGGED VALUES
; =============================================================================

#value Resistance Ohm SI
#askValues RESISTOR?

#cmdSetup combobox Resistor Main
:read: RESISTOR?
; TestController's ":readmath:" expression evaluates only ONE level of a chained ternary:
; an unparenthesized "A?a:B?b:C?c:...:z" evaluates the first "A?a:(...)" and then parses
; everything after the first ":" as a single bare comparison, never as a further ternary.
; Confirmed live: setting 19.0 kOhm wrote correctly to the instrument and read back
; 19000.000, but the combobox displayed "Short (0 Ohm)" because the whole chain collapsed
; to the boolean result of the SECOND comparison - every bucket except the first one was
; affected. Fix: wrap each nested "else" in parentheses; a parenthesized sub-expression is
; evaluated as a full ternary again, which is why the single-level readmath on the
; Actual_Resistance field below already worked without needing this.
:readmath: double(value) < 0.5 ? "0" : (double(value) < 1.45 ? "1" : (double(value) < 5.0 ? "1.9" : (double(value) < 14.5 ? "10" : (double(value) < 50.0 ? "19" : (double(value) < 145.0 ? "100" : (double(value) < 500.0 ? "190" : (double(value) < 1450.0 ? "1000" : (double(value) < 5000.0 ? "1900" : (double(value) < 14500.0 ? "10000" : (double(value) < 50000.0 ? "19000" : (double(value) < 145000.0 ? "100000" : (double(value) < 500000.0 ? "190000" : (double(value) < 1450000.0 ? "1000000" : (double(value) < 5000000.0 ? "1900000" : (double(value) < 14500000.0 ? "10000000" : (double(value) < 50000000.0 ? "19000000" : (double(value) < 500000000.0 ? "100000000" : ("20000000000"))))))))))))))))))
:write: RESISTOR
; Without a delay, TestController re-reads RESISTOR? immediately after the write and
; races the relay - confirmed live: after writing a new value, RESISTOR? still returned
; the OLD value at both 423ms and 624ms, only showing the new one by 1413ms. This is what
; looked like the combobox 'reverting' after Set - it never reverted, it read back before
; the relay finished moving. Settle time varies by which transition (some pairs settle
; under 300ms, others over 600ms), so this is set generously rather than tuned to a
; specific case.
:updatedelayed: 1.5

#cmdSetup buttons Terminals Main
; Write-only: the 6560 has no query for the current 2-wire/4-wire state (checked the
; full command list - nothing in *STB?/*ESR? either), so this can drift from the
; instrument if someone touches the front panel. Device Clear resets to 4-wire
; (manual 4.1.4); the 2-TERMINAL/4-TERMINAL front-panel LEDs are otherwise the only
; ground truth.
:write: KEY (value=="2W"?"T":"F")
:tip: 4-Wire is the default; no remote readback - check the front-panel LED if in doubt.
2-Wire 2W
4-Wire 4W
