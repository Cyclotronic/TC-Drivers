; The supply returns one response per query. TestController sends semicolon-separated
; #askValues entries as independent commands, matching the live GPIB validation.
;
; Five channels are logged rather than the obvious two, because a test cannot
; usually be re-run to recover a value nobody thought to record:
;
;   Voltage / Current       what the terminals are actually doing (MEAS:)
;   VoltageSet / CurrentSet what the supply was asked for (VOLT? / CURR?)
;   Regulation              which side the supply is regulating on
;
; Charting the measured value against its setpoint shows the output sagging away
; from the demand under load, which neither one alone reveals. Regulation catches
; the moment a load pulls the supply out of constant voltage into constant
; current - usually the point of the test, and invisible from voltage and current
; alone when the limit happens to sit where the load settles. It is logged as a
; DIGITAL value, so the column names the mode instead of printing a number and
; the chart draws it on the shared digital scale rather than as a curve:
;     bit 0 (1) = CC   constant current
;     bit 1 (2) = CV   constant voltage
; Neither bit set means the output is off or unregulated, and the column is then
; blank rather than showing 0. Both bits set has no documented meaning; it would
; show as "CC CV". Note the manual labels bit 0 "Voltage" and bit 1 "Current",
; naming the quantity that is no longer regulated rather than the mode - bit 0 is
; set when the supply is in constant current. The names here are the mode, which
; is what the column is for; do not "correct" them to match the manual's labels.
;
; The same Questionable Status register also carries overtemperature (bit 4),
; OVP tripped (bit 9) and OCP tripped (bit 10). DIGITAL cannot name those: there
; is no working way to skip a bit, so only a run of bits from 0 can be labelled.
; Nothing is lost. Those three already have their own indicators in the Main and
; Protection setup panels, reading VOLT:PROT:TRIP? and CURR:PROT:TRIP? directly,
; and a saved log keeps the raw integer whatever the display format is - so the
; file still carries every bit even when the on-screen column is blank.
;
; The bits are not latched, so this is the live state at each reading.
;
; The cost is five GPIB round trips per reading instead of two. That is hidden by
; #readingDelay 2; drop that delay for fast logging and it becomes the limit.
; Logging scope is a device mode, chosen from the mode menu rather than the
; setup panel, so it cannot be changed while logging is running and a log's
; columns stay fixed for its whole run. Two modes:
;
;   "Log All"          - Voltage, Current, VoltageSet, CurrentSet, Regulation
;   "Log V and I only" - Voltage and Current
;
; The supply has no notion of a logging mode, so the active one is held in the
; client-side variable logMode: each #cmdMode sets it, #askMode reads it back,
; and processModeString maps that to the mode name that gates #askValues and the
; #value columns. Voltage and Current carry both mode names; the three extras
; carry only Log_All. Each query keeps its trailing [20], wrapped with it, so
; the V-and-I mode drops three queries and their delays together and the two
; that remain stay 20 ms apart, which the serial path needs.
#askValues [mode:Log_All,Log_V_and_I_only]MEAS:VOLT?;[20];MEAS:CURR?;[20];[mode:Log_All]VOLT?;[20];CURR?;[20];STAT:QUES:COND?;[20];[mode:]
#value Voltage V D4 Log_All,Log_V_and_I_only
#value Current A D4 Log_All,Log_V_and_I_only
#value VoltageSet V D4 Log_All
#value CurrentSet A D4 Log_All
#value Regulation - DIGITAL(CC,CV) Log_All
#readingDelay 2
#modeChangeDelay 0.5
#askMode LogModeGet?
#cmdModeLayout 1 2

; Logging-mode plumbing. Each #cmdMode below runs one of these Set shims, which
; store the mode's token in logMode without touching the bus; LogModeGet? hands
; that token back to #askMode. The tokens are the modes' deviceModeNames (ALL,
; VI), which getFunctionModeFromDeviceMode maps to the mode names.
#scpiCmd SetModeAll none
:setvar: logMode="ALL"

#scpiCmd SetModeVI none
:setvar: logMode="VI"

#scpiCmd LogModeGet? none?
:readmath: logMode

; Exposes the front-panel display to TestController's Steps and Remote Readout
; popups: a step can write a short label to the supply's display. String
; interfaces carry no (channel) token, so TC evaluates the command as a script
; expression rather than doing a plain (value) substitution - hence the
; concatenation that wraps the text in quotes for DISP:TEXT, exactly as the
; stock display drivers do. The display holds up to 12 characters; longer text
; is truncated to 12 silently and queues no error - bench-confirmed, and not
; the -150 String data error that was expected. An embedded double quote is a
; separate trap: it closes the concatenation early, giving DISP:TEXT "AB"CD",
; which the supply rejects with -103,"Invalid separator", discards, and leaves
; the previous text in place - so that one fails safe, but silently.
#interface setReadoutString DISP:TEXT ("\""+value+"\"")

; ==============================================================================
; The whole dialog, in the order the supply gets used
; ==============================================================================
; Only the setpoint and pending-setpoint pages differ between the two rows; every
; other page is shared, so the layout does not move when the range changes.

; A single button showing the state it is in, the way the instrument's own output
; key does: grey when off, green when on.
;
; No tag sets a button's size - :labelformat: explicitly excludes buttons and
; :textwidth: only affects input fields - so the button sizes to its label.
; :nogrid: would additionally free it from the form's column grid; it is
; undocumented but used by 55 of the toggleButtons in the shipped drivers. Left
; off so the button aligns with the controls below it.
;
; The two labels differ by one character, so the button may shift very slightly as
; it toggles - the docs warn a toggleButton resizes with its label. Padding them to
; equal length only worked by adding a visible character, which was worse.

; DISP:TEXT:CLE returns the panel to its normal readout but leaves the text
; buffer holding the old string, so the :update: below used to re-read the
; message straight back into the field. Writing an empty string first empties
; the buffer - accepted with no error on an E3633A, and DISP:TEXT? then reads
; back a genuinely empty "".
#cmdSetup button Clear_Display_Message BasicSetup
:write: DISP:TEXT "";DISP:TEXT:CLE
:updatedelayed: 0.2
:update: Display_Message
:tip: Remove the message and return the display to the normal readout. If the field repopulates instead of going blank, the supply refused the empty-string write and is still reporting the last text sent - the panel itself is clear.
