; ==============================================================================
; TestController Driver Definition: HP / Agilent / Keysight E363xA DC Supplies
; ==============================================================================
; Covers the E3632A, E3633A and E3634A.  Revision 1.5 - 2026-08-23
;
; Command syntax verified against the Keysight E3633A/E3634A User's Guide
; 9018-01164 (ed. 7), the E3632A User's Guide 9018-01309 and the E363xA data
; sheet 5968-9726EN, and tested live against an E3633A (F/W 1.6-5.0-1.0) over
; GPIB. The E3633A ceilings below were read back from the instrument rather than
; taken from the data sheet: P8V 8.24 V / 20.6 A, P20V 20.60 V / 10.3 A, OVP and
; OCP both 22. The E3632A and E3634A figures are manual-derived and still need
; hardware confirmation.
;
; Notes on the E363xA command set:
;   * There is no CV/CC mode command. The supply runs in constant voltage until
;     the load reaches the current limit, then crosses into constant current by
;     itself, so there is one voltage setpoint, one current limit, and a
;     Regulation readout saying which side the hardware is on. An earlier
;     revision offered CV and CC as modes whose controls wrote the same
;     VOLT/CURR registers - do not reintroduce that.
;   * Changing the range turns the output off first. That is deliberate: it
;     avoids carrying a low-range, high-current setup into high-range voltage.
;   * GPIB and RS-232 are both built in, but only one is enabled at a time from
;     the front panel. SYST:REM and SYST:LOC are RS-232 only, so SCPIx wrappers
;     keep them off GPIB and [LOC] returns the supply to local on disconnect.
;   * Connecting does not reset the supply. Disconnecting and TestController's
;     Output Off disable the output but leave protection trips and the
;     programmed state alone.
;   * OUTP:REL is omitted deliberately - it drives optional TTL relay signals on
;     the RS-232 connector, and the manual warns against using RS-232 when those
;     are configured.
;
; Notes on the layout:
;   * The pages are real pages rather than selector targets, so TestController
;     renders them as tabs. Mixing a top-level selector with pages it does not
;     name makes those pages paint over the selector-driven content instead of
;     sitting beside it; the shapes that render correctly are "selector only" or
;     "plain pages only", and this driver is the second.
;   * The range-dependent ceilings therefore come from advNumber expressions.
;     Every page being real means Main.Output_Range exists as a variable the
;     advNumber expressions can read; Output_Range lists the four advNumbers in
;     its :update: tag so they re-evaluate on a range change.
;   * An advNumber limit line is split into exactly three whitespace-separated
;     tokens - unit, min, max - so the expression must contain no spaces at all.
;     A list written "LOW 0" becomes a fourth token and the driver fails to load
;     with "Line do not contain 3 parameters", taking the port scan down with an
;     IndexOutOfBounds. inList's default delimiter is "[|,; ]+", so "LOW,0" is
;     the same test without a space.
;
; Instrument quirks found during validation:
;   * A rejected query leaves a pending unread response, so its -420 "Query
;     UNTERMINATED" surfaces on the NEXT error read rather than its own. When
;     probing this family, read SYST:ERR? after every single query or the blame
;     lands one command late.
;   * VOLT:STEP? and CURR:STEP? do NOT accept MIN, MAX or DEF as query
;     arguments, even though VOLT:STEP DEF is a valid setting command. Only the
;     bare query works, so the step floors below are literals.
;   * VOLT? MAX / CURR? MAX do work, and follow the selected range.
;
; This driver claims the same three #idString values as the shipped
; "AgilentHP E363xA.TXT". Only one can win the match - move the stock file out
; of the Devices folder to use this one.
;
; Published at https://github.com/Cyclotronic/TC-Drivers - see PUBLISHING.md
; before changing anything that goes out with it.
; ==============================================================================

; The supply returns one response per query. TestController sends semicolon-separated
; #askValues entries as independent commands, matching the live GPIB validation.
;
; Five channels are logged rather than the obvious two, because a test cannot
; usually be re-run to recover a value nobody thought to record:
;
;   Voltage / Current       what the terminals are actually doing (MEAS:)
;   VoltageSet / CurrentSet what the supply was asked for (VOLT? / CURR?)
;   Regulation              which side the supply is regulating on
;
; Charting the measured value against its setpoint shows the output sagging away
; from the demand under load, which neither one alone reveals. Regulation catches
; the moment a load pulls the supply out of constant voltage into constant
; current - usually the point of the test, and invisible from voltage and current
; alone when the limit happens to sit where the load settles. It is logged as the
; raw register value so it charts as steps:
;     0 = output off or unregulated   1 = constant current
;     2 = constant voltage            3 = regulation fault
; The bits are not latched, so this is the live state at each reading.
;
; The cost is five GPIB round trips per reading instead of two. That is hidden by
; #readingDelay 2; drop that delay for fast logging and it becomes the limit.
; Logging scope is a device mode, chosen from the mode menu rather than the
; setup panel, so it cannot be changed while logging is running and a log's
; columns stay fixed for its whole run. Two modes:
;
;   "Log All"          - Voltage, Current, VoltageSet, CurrentSet, Regulation
;   "Log V and I only" - Voltage and Current
;
; The supply has no notion of a logging mode, so the active one is held in the
; client-side variable logMode: each #cmdMode sets it, #askMode reads it back,
; and processModeString maps that to the mode name that gates #askValues and the
; #value columns. Voltage and Current carry both mode names; the three extras
; carry only Log_All. Each query keeps its trailing [20], wrapped with it, so
; the V-and-I mode drops three queries and their delays together and the two
; that remain stay 20 ms apart, which the serial path needs.
#askValues [mode:Log_All,Log_V_and_I_only]MEAS:VOLT?;[20];MEAS:CURR?;[20];[mode:Log_All]VOLT?;[20];CURR?;[20];STAT:QUES:COND?;[20];[mode:]
#value Voltage V D4 Log_All,Log_V_and_I_only
#value Current A D4 Log_All,Log_V_and_I_only
#value VoltageSet V D4 Log_All
#value CurrentSet A D4 Log_All
#value Regulation - D0 Log_All
#readingDelay 2
#modeChangeDelay 0.5
#askMode LogModeGet?
#cmdModeLayout 1 2

; SYST:REM/SYST:LOC are valid only for RS-232 on this family.
#scpiCmd SerialInit #pgm#
if (portType!="GPIB")
  deviceWrite(handle,"SYST:REM");
endif;

#scpiCmd SerialExit #pgm#
if (portType!="GPIB")
  deviceWrite(handle,"SYST:LOC");
endif;

; SCPIx sends this interface-control token only for a GPIB connection.
#scpiCmd GpibExit
[LOC]

; Quote the user text required by DISP:TEXT while keeping the setup control simple.
#scpiCmd SetDisplayText tx DISP:TEXT "(value)"

; Logging-mode plumbing. Each #cmdMode below runs one of these Set shims, which
; store the mode's token in logMode without touching the bus; LogModeGet? hands
; that token back to #askMode. The tokens are the modes' deviceModeNames (ALL,
; VI), which getFunctionModeFromDeviceMode maps to the mode names.
#scpiCmd SetModeAll none
:setvar: logMode="ALL"

#scpiCmd SetModeVI none
:setvar: logMode="VI"

#scpiCmd LogModeGet? none?
:readmath: logMode

; The two selectable logging modes. The command that backs each one only sets
; the client variable - nothing is sent to the supply.
#cmdMode Log_All ALL
SetModeAll

#cmdMode Log_V_and_I_only VI
SetModeVI

#initCmd SetModeAll;SerialInit;
#finalCmd OUTP OFF;[*OPC];SerialExit;GpibExit
#outputOff OUTP OFF

; Exposes the front-panel display to TestController's Steps and Remote Readout
; popups: a step can write a short label to the supply's display. String
; interfaces carry no (channel) token, so TC evaluates the command as a script
; expression rather than doing a plain (value) substitution - hence the
; concatenation that wraps the text in quotes for DISP:TEXT, exactly as the
; stock display drivers do. The display holds up to 12 characters; longer text
; is truncated to 12 silently and queues no error - bench-confirmed, and not
; the -150 String data error that was expected. An embedded double quote is a
; separate trap: it closes the concatenation early, giving DISP:TEXT "AB"CD",
; which the supply rejects with -103,"Invalid separator", discards, and leaves
; the previous text in place - so that one fails safe, but silently.
#interface setReadoutString DISP:TEXT ("\""+value+"\"")

; ==============================================================================
; The whole dialog, in the order the supply gets used
; ==============================================================================
; Only the setpoint and pending-setpoint pages differ between the two rows; every
; other page is shared, so the layout does not move when the range changes.

; A single button showing the state it is in, the way the instrument's own output
; key does: grey when off, green when on.
;
; No tag sets a button's size - :labelformat: explicitly excludes buttons and
; :textwidth: only affects input fields - so the button sizes to its label.
; :nogrid: would additionally free it from the form's column grid; it is
; undocumented but used by 55 of the toggleButtons in the shipped drivers. Left
; off so the button aligns with the controls below it.
;
; The two labels differ by one character, so the button may shift very slightly as
; it toggles - the docs warn a toggleButton resizes with its label. Padding them to
; equal length only worked by adding a visible character, which was worse.
